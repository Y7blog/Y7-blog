假如你做了一个 NFT 盲盒：1 万个盒子，里面有普通、稀有、史诗、传说四个档位，传说只有 2%。

盒子卖完了，开盒的时候，有人开出了传说，立刻有人在群里问：**“这真是随机开出来的？还是你们偷偷把传说留给了自己人？”**

你怎么证明？把代码贴出来也没用——代码只能证明“规则是这么写的”，证明不了“这次的结果真是按规则跑出来的”。链上的数据全公开，任何人都能盯着看，口头保证在这里是不值钱的。

这就是 VRF 真正派上用场的地方。VRF 给出的随机数后面跟一份证明，谁都能验。这篇就看它到底能用在哪——**NFT 盲盒、链上抽奖、区块链游戏**，这三个场景，恰好是 VRF 最常见的用处。

> 💡 **先说清楚**：这篇文章讲 Chainlink VRF 的实际用途，帮你理解可验证随机数在真实项目里是怎么用的。本文是知识科普，不是投资建议；涉及真金白银的合约逻辑，上线前一定要经过专业审计，先在测试网把流程跑通。

## 一、先看总表：VRF 到底适合干什么

VRF 不是万能的。它最适合的，是**结果只有一次、价值比较高、所有人都要信服**的场景。下面这张表，先把这篇要讲的全部用处列出来：

| 用处 | 随机数用来决定什么 | 为什么需要 VRF | 典型例子 |
| --- | --- | --- | --- |
| NFT 盲盒开盒 | 每个 NFT 的属性和稀有度 | 开出传说的人要让所有人相信不是内定的 | Aavegotchi、Axie Origin Axies |
| NFT 随机发放 | 买家拿到的是哪一个 NFT | 防止项目方把稀有的挑出来自己留着 | 随机掉落、抽卡 |
| 链上抽奖 | 谁是中奖者 | 奖金越大，越要证明没动手脚 | PoolTogether 无损抽奖 |
| 游戏掉落与开箱 | 掉什么装备、开出什么道具 | 稀有装备值钱，玩家要确信爆率是真的 | 链游战利品箱 |
| 游戏内关键事件 | 暴击、地图生成、回合顺序 | 结果影响胜负，输家要服气 | 回合制链游、卡牌游戏 |
| 随机分配与抽样 | 随机挑人、随机分任务 | 被挑中的人要相信不是针对他 | DAO 陪审团、随机抽查 |

还有一类场景，这篇后面会专门讲：**不适合用 VRF 的**。先把适合的讲清楚，再讲不适合的，你才知道边界在哪。

## 二、NFT 盲盒：稀有度是怎么定出来的？

先从最常见的场景开始。NFT 盲盒的玩法，很多人都见过：先花钱买一个盒子，盒子打开之前，你不知道里面是什么。开盒之后，有人拿到普通，有人拿到传说。

问题是：**开盒这个动作，到底是怎么决定你拿到什么的？**

### 两种开盒方式

实际项目里，常见两种做法：

**第一种：Mint 的时候直接定属性。**

你付钱 Mint，合约当场向 VRF 要一个随机数，用这个随机数算出这个 NFT 的属性，当场就写进链上。Aavegotchi 就是这么做的：玩家打开一个 Portal（可以理解成一个召唤门），VRF 给出的随机数决定了召唤出来的 Aavegotchi 长什么样、属性是多少。Axie Infinity 的 Origin Axies 也是类似的路子：VRF 的随机数决定了每只 Origin Axie 的身体部位组合，稀有的组合就这么随机产生了。

**第二种：先 Mint 一个看不见的盒子，之后统一开奖。**

先卖盒子，盒子本身长得都一样，谁也不知道里面是什么。等卖完（或者到了约定时间），项目方用 VRF 要一批随机数，一次性给所有盒子定属性，再统一揭晓。这种做法多了一个好处：**没人能挑盒子**。如果 Mint 的时候就定好了属性，懂行的人可以盯着链上的数据，只买那些还没被 Mint 走的稀有属性对应的盒子——这叫“狙击稀有”。先卖盒子、后统一开奖，狙击就没用了，因为开奖之前，谁也不知道哪个盒子里面是什么。

两种方式没有绝对的好坏，关键是：**随机数必须在开盒结果确定之前就已经“锁死”，而且谁都改不了**。VRF 的请求—回调机制正好满足这一点：请求发出的时候，随机数还不存在；随机数算出来之后，证明已经验过了，改不了。

### 稀有度是怎么用一个数字算出来的？

不管哪种方式，核心都是一段很简单的算术。假设稀有度的分布是这么定的：

| 档位 | 概率 | 随机数落在哪个区间 |
| --- | --- | --- |
| 普通 | 60% | 0–59 |
| 稀有 | 30% | 60–89 |
| 史诗 | 8% | 90–97 |
| 传说 | 2% | 98–99 |

合约拿到 VRF 给的随机数之后，先对 100 取模，得到一个 0 到 99 之间的数，再看这个数落在哪个区间，就定下来是哪个档位。比如随机数取模之后是 97，那就是史诗；是 99，那就是传说。

```
随机数（256 位的大数字）
    │
    ├─→ % 100 → 得到 0–99 之间的一个数
    │
    └─→ 看落在哪一个区间
            0–59   → 普通（60%）
            60–89  → 稀有（30%）
            90–97  → 史诗（8%）
            98–99  → 传说（2%）
```

这里有一个新手经常会问的问题：**取模会不会让概率变歪？**

答案是：用 VRF 给的 256 位随机数来取模，偏差小到可以忽略。256 位的数字有 2 的 256 次方种可能，100 整除不了它，确实会有一点点不均匀——但那点偏差，比你中传说的概率本身还要小无数倍，现实中完全不用担心。官方的最佳实践文档也是这么教的：直接用 `randomWords[0] % 100` 这种写法就行。

真正要小心的不是取模本身，而是**概率表写错了**。比如你想让传说是 2%，结果区间写成了 98–100，传说就变成了 3%。VRF 只能保证随机数是干净的，保证不了你写的概率表是对的。概率表是开发者自己写的，写错了，VRF 也救不了你。

### 一个随机数能开几个盒子？

有时候一个项目要一次开几百个盒子，难道要向 VRF 请求几百次吗？

不用。一次请求最多可以要 500 个随机数（Sepolia 和主网都是这个上限），但每个随机数都要多花 Gas 和钱。更省钱的做法是：**只请求一个随机数，再用哈希把它“展开”成多个**。

```
拿到一个随机数 randomWord
    │
    ├─→ keccak256(randomWord, 0) → 第 1 个盒子的随机数
    ├─→ keccak256(randomWord, 1) → 第 2 个盒子的随机数
    ├─→ keccak256(randomWord, 2) → 第 3 个盒子的随机数
    └─→ ……以此类推
```

哈希的特点是：输入变一点点，输出就完全不同。所以拿一个可信的随机数做种子，展开出来的每一个值也都是不可预测的。官方文档和很多实战文章都推荐这种做法：**大多数场景下，一个随机数就够了，剩下的在合约里自己展开**。除非你确实需要多个完全独立的随机数，才一次多要几个。

## 三、链上抽奖：从报名到开奖的完整流程

抽奖是最能体现 VRF 价值的场景。因为抽奖的规则人人都懂——交了钱、抽一个人、拿走奖金——所以一旦结果出来，所有人的眼睛都盯在“公不公平”这四个字上。

### 一个真实的例子：PoolTogether

先看一个已经跑了很多年的真实项目：PoolTogether。它做的是“无损抽奖”——大家把钱存进一个池子，池子产生的利息攒起来当奖金，定期抽一个人拿走全部利息，其他人拿回自己的本金，一分钱不亏。

这个模式能成立，有一个前提：**抽奖的人必须相信，中奖者真的是随机抽出来的**。如果项目方能偷偷指定中奖者，整个模式就崩了。PoolTogether 用的就是 Chainlink VRF：每期开奖，合约向 VRF 要一个随机数，用随机数对参与人数取模，算出中奖者。整个过程都在链上，谁都能查、谁都能验。

### 抽奖合约的四个阶段

一个标准的链上抽奖，流程是这样的：

```
第 1 阶段：报名
    │
    │  用户交钱报名，名单写进合约
    │  报名有截止时间，到了就关门
    │
第 2 阶段：截止
    │
    │  报名截止，名单锁死
    │  截止之后，谁也不能再报名
    │
第 3 阶段：请求随机数
    │
    │  合约向 VRF 发请求，等回调
    │  这个时候，结果还没出来，谁也不知道
    │
第 4 阶段：开奖
    │
    │  回调到了，合约用随机数算出中奖者
    │  中奖者 = 随机数 % 参与人数
    │  奖金自动发给中奖者，全程上链
```

每个阶段都有自己的规矩，违反任何一条，公平性就破了：

- **截止之后不能再报名。** 如果请求已经发出了，还有人能挤进名单，那名单就是可以被操控的。官方文档写得很明确：合约在提交随机数请求之后，**不应该再接受任何用户提供的输入**。
- **不能因为结果不满意就重新请求。** 这是最重要的一条。假设开奖结果出来了，是项目方不喜欢的人中奖，项目方再发一次请求、重新抽一次——这就是作弊。官方文档直接把这种做法列为错误用法：**任何重新请求或取消随机数的行为，都是对 VRF 的不正确使用**。
- **回调不能失败。** 回调函数 `fulfillRandomWords` 里写的是开奖逻辑——算中奖者、发奖金。如果这个函数执行失败（比如 Gas 不够、逻辑出错），VRF 不会再调第二次。随机数就白白浪费了，钱照扣，奖也没开成。所以回调里的逻辑要尽量简单，Gas 上限要留够。

### 一个最小的抽奖合约长什么样？

把上面的流程写成代码，核心其实就几十行。这里只看最关键的部分，完整版留到下一篇的实战里：

```
contract Lottery is VRFConsumerBaseV2Plus {
    // 报名名单
    address[] public players;
    // 每一轮的请求编号对应哪一轮
    mapping(uint256 => uint256) public requestIdToRound;

    // 开奖：向 VRF 要一个随机数
    function drawWinner() external {
        uint256 requestId = s_vrfCoordinator.requestRandomWords(...);
        // 记下来：这个请求编号对应的是第几轮
        requestIdToRound[requestId] = currentRound;
    }

    // 回调：随机数到了，算出中奖者
    function fulfillRandomWords(uint256 requestId, uint256[] calldata randomWords)
        internal override
    {
        uint256 winnerIndex = randomWords[0] % players.length;
        address winner = players[winnerIndex];
        // 发奖金
        payable(winner).transfer(address(this).balance);
    }
}
```

注意两个细节：

- **`requestIdToRound` 这个映射是必需的**。如果同时有好几轮抽奖在跑，回调回来的时候，你得知道这个随机数对应的是哪一轮。官方最佳实践文档专门讲了这一点：同时处理多个 VRF 请求的时候，一定要用映射把请求编号和业务状态对应起来。
- **中奖者是 `randomWords[0] % players.length`**。取模之后的结果是 0 到参与人数减 1 之间的一个数，正好对应名单里的一个位置。

费用方面，给你一个参考：2026 年在以太坊主网上，一次 VRF 请求的费用大概是 0.1 到 0.5 个 LINK，再加上回调的 Gas。这个数字会随着 LINK 的价格和 Gas 价格波动，具体以官方文档的计费页面为准。对于一个奖金池几千上万的抽奖来说，这点成本完全可以接受；但如果你的抽奖奖金本身只有几美元，那就要先算算账了。

## 四、区块链游戏：暴击、掉落、地图生成

游戏是 VRF 用得最多的地方，也是最容易用错的地方。因为游戏里的随机太多了：暴击、掉落、开箱、抽卡、地图生成、匹配对手、回合顺序……不是每一种随机都适合用 VRF。

### 适合用 VRF 的：结果影响大、频率低

**开箱和抽卡。** 玩家花钱开一个箱子，里面可能开出价值很高的装备。开箱的结果直接关系到玩家的钱，值得用 VRF。很多链游的战利品箱就是这么做的：箱子打开的那一刻，合约向 VRF 要随机数，随机数决定了箱子里是什么。

**稀有掉落。** 打怪掉装备，掉不掉稀有装备、掉的是哪一件，都可以用 VRF 定。特别是那种全服公告的稀有掉落——“恭喜 XX 打出了传说武器”——这种结果越公开，越需要一份谁都能验的证明。

**地图和关卡生成。** 有些游戏的地图是随机生成的：每次进一个新区域，地形、宝箱位置、敌人分布都不一样。用 VRF 生成地图种子，玩家可以确信地图不是针对他量身定做的。

**回合顺序和匹配种子。** 两个人对战，谁先手？匹配的时候按什么种子分组？这些“开局之前就要定下来、而且影响胜负”的随机，适合用 VRF。

### 不适合用 VRF 的：频率太高、价值太低

VRF 有两个特点，决定了它不适合高频场景：

- **要等。** 请求发出之后，要等几个区块，回调才会到。Sepolia 上通常要一分钟左右。实时对战游戏里，每回合都要掷一次骰子，等一分钟才出结果，玩家早就关游戏了。
- **要花钱。** 每次请求都要付 LINK 和 Gas。一个游戏如果每走一步都要一个随机数，费用会把游戏本身的收入吃掉。

所以，**每一局、每一回合都要随机数的游戏，一般不用 VRF**。这些场景更常见的替代方案是：

| 方案 | 适合什么 | 代价 |
| --- | --- | --- |
| Chainlink VRF | 低频、高价值、要人人信服的随机 | 每次请求要花钱、要等几个区块 |
| commit-reveal（承诺—揭示） | 多人参与、大家互相监督的随机 | 要两笔交易、参与者必须配合揭示 |
| block.prevrandao（以太坊的 RANDAO） | 低价值、随手要的随机 | 出块者能有 1 个比特的影响力，轻微可偏 |
| 链下服务器给随机数 | 完全不上链的内部逻辑 | 玩家只能选择相信你 |

怎么选，核心就看两个问题：**这个随机结果值多少钱？有多少人在盯着它？** 结果越值钱、盯着的人越多，越值得用 VRF。只是一个小游戏里的装饰性随机——比如 NPC 随口说一句随机台词——那用链上凑个随机数就够了，根本没必要上 VRF。

### 游戏里常见的错误用法

还有一个经常犯的错：**把 VRF 的随机数和别的随机源混在一起，以为这样更随机**。

直觉上，两个随机源加在一起，应该比一个更随机。但实际情况是：如果第二个随机源是某个参与者后来才提供的，那他可以在看到第一个随机数之后，挑一个对自己有利的第二个值。VRF 的随机数本身已经不可预测、不可篡改，再混一个后来才定的输入进去，不但没更安全，反而多了一个可以被动手脚的地方。正确的做法是：**VRF 的随机数本身就是结果，不要再往里面掺东西**。如果你实在想多加一层保险，那要确保所有输入都在 VRF 请求发出之前就已经定死，谁也不能事后改。

## 五、除了游戏和抽奖，VRF 还能用在哪

VRF 的用处不止上面三个。官方文档里还列了另外两类，用得少，但很能说明 VRF 的本质：

**随机分配职责和资源。** 比如一个 DAO 要随机选几个成员当陪审团，裁决一个争议；或者一个项目要随机分配一批有限的名额。被选中的人要相信自己不是被针对的，没被选中的人要相信不是被排挤的。VRF 的随机数加证明，正好解决这个信任问题。

**随机抽样。** 比如一个共识机制要从所有验证者里随机抽一小部分来投票，或者一个审计系统要从一大批交易里随机抽几笔来检查。抽样的公平性，同样需要一份谁都能验的证明。

这两类场景的共同点是：**随机数本身不值钱，但“随机”这个过程必须让人信服**。VRF 解决的从来不只是“怎么生成随机数”，而是“怎么让所有人相信这个随机数是干净的”。想明白这一点，你就能自己判断一个新场景该不该用 VRF：问一句“如果结果出来，有人质疑公平性，我拿什么证明？”——如果答不上来，VRF 可能就是你要找的东西。

## 六、动手之前，先想清楚这三个问题

到这里，VRF 的三大用处都讲完了。动手写合约之前，先问自己三个问题：

**第一，这个随机结果值多少钱？**

奖金几千上万的抽奖、传说装备的掉落、1 万个 NFT 的稀有度分配——这些都值得用 VRF。一个免费小游戏里的装饰性随机，不值得。

**第二，多久要一次随机数？**

一天一次、一局一次、开箱一次——这个频率，VRF 完全跟得上。每走一步、每回合都要一次——VRF 跟不上，要换别的方案。

**第三，结果出来之后，有人质疑怎么办？**

如果你的回答是“链上有证明，谁都能自己验”，那 VRF 就是对的。如果你的回答是“相信我就行”，那不管用不用 VRF，这个项目都有问题。

还有一句话，是上一篇结尾也提过的，这里再说一次，因为它太容易被忘了：**VRF 解决的是“随机数可不可信”，不是“规则公不公平”**。抽奖规则本身写得有问题——比如中奖概率算错了、有人能重复参加——VRF 也救不了你。随机数是干净的，规则是人写的，规则的公平性，还得靠你自己把账算清楚。

---

## 总结

- VRF 最适合的场景是：结果只有一次、价值比较高、所有人都要信服。NFT 盲盒、链上抽奖、区块链游戏里的关键随机，就是这三类。
- NFT 盲盒有两种开法：Mint 时直接定属性，或者先卖盒子、之后统一开奖。后者能防止有人盯着链上数据狙击稀有盒子。
- 稀有度是用取模算出来的：随机数对 100 取模，看落在哪个概率区间。256 位随机数的取模偏差小到可以忽略，真正要小心的是概率表本身有没有写错。
- 一个随机数就够开很多盒子：用哈希把一个随机数展开成多个，比一次要几百个随机数省钱得多。单次请求最多 500 个随机数。
- 链上抽奖分四个阶段：报名、截止、请求随机数、回调开奖。三条铁律：截止后不能再报名、不能因为结果不满意重新请求、回调失败不会重试。
- 真实案例：Aavegotchi 用 VRF 决定召唤出来的角色属性，Axie Infinity 用 VRF 生成 Origin Axie 的身体部位，PoolTogether 用 VRF 抽无损抽奖的中奖者。
- 游戏里要分清楚：开箱、稀有掉落、地图生成、回合顺序这些低频高价值的随机适合 VRF；每回合都要的随机不适合，又贵又慢，可以考虑 commit-reveal 或者以太坊自带的 prevrandao。
- 不要把 VRF 的随机数和其他随机源混在一起。VRF 的随机数本身已经不可预测，再掺一个事后才定的输入，反而多了一个动手脚的地方。
- VRF 之外，随机分配职责、随机抽样这些场景也在用它。本质都一样：随机数本身不值钱，但“随机”这个过程必须让人信服。
