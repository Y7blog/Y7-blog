**从 0 理解钱包地址、公钥、私钥、哈希，以及一笔交易是如何证明“这是你授权的”。**

上一篇，我们从「状态机」的角度重新认识了区块链。

[[y7blog-web3-02]]

简单来说：

> **区块链可以理解成一个由分布式网络共同维护的状态机。**

用户发起交易，交易按照规则执行，然后推动区块链的状态发生变化。

但这里马上会出现一个非常重要的问题：

**区块链凭什么知道，这笔交易真的是你发起的？**

比如：

```text
Alice：100 Token

Alice → Bob：10 Token
```

如果有人随便写一笔：

```text
Alice → Bob：100 Token
```

网络为什么不能直接接受？

如果我只知道你的钱包地址，是不是就可以冒充你？

答案当然是否定的。

而让这个系统能够运行起来的关键技术之一，就是：

> **密码学。**

不过这里有一个非常容易产生的误解。

很多人第一次听到“密码学”，会以为：

> “是不是区块链上的所有数据都是加密的？”

其实并不是。

区块链使用密码学，并不只是为了“把数据藏起来”。

它更重要的作用是帮助系统解决：

- 怎么证明一笔交易是谁授权的？
- 怎么防止别人冒充你？
- 怎么发现交易数据有没有被篡改？
- 怎么让网络在不获得私钥的情况下验证签名？

而这篇文章最重要的几个概念就是：

* 私钥
* 公钥
* 钱包地址
* 哈希
* 数字签名

接下来，我们一个一个拆开。

---

# 01｜为什么区块链离不开密码学？

先想一个我们非常熟悉的场景。

你去银行转账。

打开银行 App：

```text
收款人：Bob
金额：100 元
```

点击确认之后，银行服务器知道：

> 这是 Alice 的账户。

然后银行修改数据库：

```text
Alice：-100 元
Bob：+100 元
```

整个过程背后有一个中心机构：

**银行。**

银行负责维护账户，也负责判断：

> “这个人有没有权限操作这个账户？”

但区块链没有一个这样的中心服务器。

网络里可能存在：

```text
Node A
Node B
Node C
Node D
...
```

那么 Alice 想转 10 Token 给 Bob：

```text
Alice → Bob：10 Token
```

网络怎么知道：

> **这个 Alice 真的是这个账户的控制者？**

如果没有可靠的证明方式，任何人都可以伪造：

```text
Alice → Bob：1000000 Token
```

然后告诉网络：

> “这是 Alice 发的。”

显然不行。

所以区块链需要一种方式，让用户能够证明：

> **“这笔交易确实经过我的授权。”**

但同时又不能把用户的秘密交给网络。

这就是密码学发挥作用的地方。

---

# 02｜密码学到底是什么？

“密码学”听起来很专业。

其实可以先把它理解成：

> **利用数学规则保护信息、证明身份和验证数据的一套技术。**

区块链中的密码学并不只是“加密”。

对于我们今天讨论的钱包和交易来说，可以先关注三个作用：

```text
            私钥
             ↓
          控制账户

          数字签名
             ↓
          证明授权

            哈希
             ↓
生成数据摘要、帮助验证数据完整性
```

这三个概念之后会不断出现。

尤其是：

> **哈希 + 数字签名**

是理解区块链交易非常重要的一条线。

---

# 03｜什么是私钥？为什么它如此重要？

先从最重要的开始：

**私钥（Private Key）。**

如果用最简单的话解释：

> **私钥是一段需要由你自己保管的秘密数据，它是控制对应账户的重要密码学凭证。**

你可以暂时把它想象成一把：

> **只有你拥有的钥匙。**

但它和我们现实中的钥匙不完全一样。

它本质上是一段符合特定规则的随机数据。

例如可以想象成：

```text
私钥：

7a3f...9c21
```

真实私钥通常是一串非常长的十六进制数据。

它最重要的特点就是：

> **必须保密。**

为什么？

因为私钥可以用于生成数字签名。

而数字签名可以用于授权交易。

简单理解：

```text
      私钥
       ↓
      签名
       ↓
交易获得授权证明
```

所以如果别人获得了你的私钥，他可能就拥有控制对应账户资产的能力。

因此：

```text
钱包地址：
可以公开

私钥：
必须保密
```

这也是 Web3 钱包安全的第一原则。

---

# 04｜什么是公钥？

理解私钥之后，再来看：

**公钥（Public Key）。**

公钥和私钥是一对密码学密钥。

在很多区块链使用的非对称密码学体系中，可以简单理解为：

```text
   私钥
    ↓
密码学算法
    ↓
   公钥
```

这里需要特别注意：

> **公钥不是私钥简单“加密”出来的字符串。**

而是通过特定的密码学算法，根据私钥计算得到。

以 Ethereum 使用的 secp256k1 椭圆曲线体系为例：

```text
    私钥
     ↓
椭圆曲线计算
     ↓
    公钥
```

而从公钥反推出私钥，在计算上应该是不可行的。

所以：

```text
私钥 → 公钥
```

很容易。

但：

```text
公钥 → 私钥
```

并不能通过正常计算反推出来。

这正是公钥密码学能够工作的基础之一。

---

# 05｜钱包地址到底是怎么来的？

这一部分非常容易被初学者搞混。

先纠正一个常见说法：

> **钱包地址不等于公钥。**

更准确的关系应该理解成：

```text
           私钥
            ↓
         生成公钥
            ↓
根据具体区块链的地址规则处理
            ↓
        得到钱包地址
```

也就是说：

**私钥、公钥、钱包地址是三个不同的概念。**

以 Ethereum / EVM 地址为例，可以进一步理解：

```text
      私钥
       ↓
    生成公钥
       ↓
 Keccak-256 哈希
       ↓
取结果的最后 20 字节
       ↓
  Ethereum 地址
```

因此，一个 Ethereum 地址通常表现为：

```text
0x1234...abcd
```

这里的 `0x` 表示十六进制表示。

而 Bitcoin、Solana 等区块链的地址生成规则又不同。

例如 Solana 的地址本质上与公钥直接相关，并使用 Base58 等方式表示。

所以不要把下面这句话当成所有区块链都适用的公式：

```text
钱包地址 = 公钥
```

更准确的理解应该是：

> **钱包地址是区块链协议根据公钥等信息按照特定规则生成的账户标识。**

这也是为什么不同区块链的钱包地址长得完全不一样。

---

# 06｜公钥、私钥、钱包地址到底是什么关系？

现在把三个概念放在一起：

```text
             私钥
               │
               │ 密码学计算
               ↓
             公钥
               │
               │ 地址生成规则
               ↓
           钱包地址
```

注意，这里是一个**概念上的关系图**。

不同区块链的具体实现会有所区别。

可以简单记：

### 私钥

> 控制账户的重要秘密凭证。

### 公钥

> 由私钥通过密码学算法生成，可以公开。

### 钱包地址

> 根据区块链协议规则生成的账户标识，可以公开给别人用于收款。

所以：

```text
私钥：不能公开
公钥：通常可以公开
地址：可以公开
```

比如你可以在网上公布：

```text
我的钱包地址：

0xABCDEF...
```

别人可以向这个地址转账。

但是你不能公布：

```text
我的私钥：

0x......
```

因为地址是“别人怎么找到你”。

而私钥则关系到：

> **谁有权限控制这个账户。**

---

# 07｜哈希到底是什么？为什么区块链到处都有它？

到这里，我们还缺一个非常重要的概念：

**Hash，哈希。**

如果说私钥、公钥解决的是：

> “谁有权限？”

那么哈希主要帮助我们解决：

> **“这份数据有没有变化？”**

你可以把哈希理解成：

> **把任意长度的数据，通过一个确定的算法计算成一个固定长度的数字指纹。**

例如：

```text
原始数据：

Hello Blockchain
```

经过哈希：

```text
Hash：

某一串固定长度的数据
```

如果原始数据发生一点变化：

```text
Hello Blockchain!
```

重新计算哈希之后，结果会完全不同。

可以简单理解：

```text
数据 A
 ↓
Hash
 ↓
摘要 A
```

如果：

```text
数据 A ≠ 数据 B
```

那么它们产生相同哈希的概率应该非常低。

因此哈希特别适合做：

- 数据完整性验证
- 交易数据摘要
- 区块之间的关联
- Merkle Tree
- 交易 ID / 数据标识
- 数字签名中的消息摘要

区块链中经常使用不同的哈希算法。

例如 Ethereum 大量使用：

> **Keccak-256**

Bitcoin 则大量使用：

> **SHA-256**

这里先不用记算法细节。

你只需要先建立一个直觉：

> **哈希就像数据的“指纹”。**

---

# 08｜哈希和数字签名到底是什么关系？

现在终于进入这篇文章最关键的一部分。

很多初学者会以为：

```text
  交易
   ↓
  私钥
   ↓
数字签名
```

这个理解还不够完整。

在实际的区块链交易签名过程中，通常可以抽象成：

```text
    交易数据
       ↓
  编码 / 序列化
       ↓
      哈希
       ↓
  得到消息摘要
       ↓
使用私钥进行签名
       ↓
    数字签名
```

也就是说：

> **哈希通常是数字签名流程中的重要一步。**

为什么不直接对整笔交易数据进行签名？

因为交易可能包含很多数据。

先通过哈希把它转换成固定长度的摘要：

```text
  一大段交易数据
        ↓
      Hash
        ↓
   固定长度摘要
```

然后对这个摘要进行签名。

这样更加适合密码学签名算法处理。

更重要的是：

如果交易内容被修改：

```text
转账 10 Token
```

变成：

```text
转账 100 Token
```

那么：

```text
原交易
  ↓
Hash A
```

和：

```text
被修改后的交易
     ↓
   Hash B
```

会得到不同的结果。

于是原来的签名就无法对应新的交易内容。

这意味着：

> **签名不仅可以帮助证明“谁授权了这笔交易”，还可以帮助发现交易内容是否被篡改。**

所以可以把两者的作用简单分开：

```text
        哈希
         ↓
把数据变成固定长度摘要
         ↓
  帮助保证数据完整性


     数字签名
        ↓
使用私钥对消息进行授权
        ↓
   其他人可以验证
```

二者结合起来，就构成了区块链交易验证的重要基础。

---

# 09｜什么是数字签名？

现在再来看：

**Digital Signature，数字签名。**

你可以把它理解成：

> **账户控制者使用私钥，对一条消息或交易进行密码学授权后产生的证明。**

假设 Alice 想给 Bob 转 10 Token。

首先创建交易：

```text
From：

Alice

To：

Bob

Amount：

10 Token
```

然后进行签名流程。

简化之后：

```text
  交易数据
     ↓
    哈希
     ↓
  消息摘要
     ↓
Alice 的私钥
     ↓
  数字签名
```

最终得到：

```text
  交易
   +
数字签名
```

然后广播到网络。

节点收到之后，可以使用对应的公开信息验证：

```text
   交易
    +
 数字签名
    +
公钥相关信息
```

如果验证成功：

```text
签名有效
```

网络就可以确认：

> **这笔交易与对应账户的密码学授权关系是成立的。**

这里一定要注意：

> **签名并不是把交易“加密起来”。**

数字签名和数据加密解决的是不同的问题。

简单区分：

```text
加密：
别人看不懂内容

签名：
证明是谁授权，并验证数据是否匹配
```

区块链交易通常需要的是后者。

---

# 10｜为什么别人可以验证签名，却不知道你的私钥？

这正是密码学最巧妙的地方之一。

Alice：

```text
      私钥
       ↓
对交易摘要进行签名
       ↓
    数字签名
```

然后把：

```text
  交易
   +
数字签名
```

广播到网络。

其他节点不需要知道 Alice 的私钥。

它们只需要使用公开信息验证：

> **这个签名是否与这笔交易以及对应的公钥相匹配？**

所以：

```text
Alice 手里：

私钥
```

网络看到：

```text
  交易
   +
  签名
   +
公开信息
```

验证结果：

```text
✓ 签名有效
```

如果有人修改交易：

```text
10 Token
```

改成：

```text
100 Token
```

那么新的交易数据经过哈希后：

```text
Hash A
```

会变成：

```text
Hash B
```

原来的签名就不能直接证明修改后的内容是 Alice 授权的。

因此：

> **私钥负责产生签名，公开信息负责验证签名，而哈希把交易内容变化反映到签名验证过程中。**

这三者终于串起来了：

```text
  交易
   ↓
  哈希
   ↓
消息摘要
   ↓
  私钥
   ↓
数字签名
   ↓
公钥验证
```

# 11｜一笔区块链交易到底是怎么被签名的？

现在把上一篇文章的“状态机”和这一篇的“密码学”连接起来。

假设：

```text
Alice：100 Token
Bob：50 Token
```

Alice 想给 Bob 转：

```text
10 Token
```

可以把整个过程简化成：

```text
①         创建交易
             ↓
②     对交易数据进行编码
             ↓
③       计算交易哈希
             ↓
④ 使用 Alice 的私钥进行签名
             ↓
⑤     广播交易 + 签名
             ↓
⑥      网络节点验证签名
             ↓
⑦   验证交易是否符合协议规则
             ↓
⑧       交易被纳入区块
             ↓
⑨         执行交易
             ↓
⑩     区块链状态发生变化
```

最终：

```text
Alice：90 Token
Bob：60 Token
```

这样一来，两篇文章的内容就连接起来了。

上一篇我们讲：

```text
  交易
   ↓
状态转换
   ↓
 新状态
```

这一篇讲：

```text
  交易
   ↓
  哈希
   ↓
私钥签名
   ↓
节点验证
```

合在一起就是：

```text
                 用户
                  │
                  ↓
               创建交易
                  │
                  ↓
             交易数据哈希
                  │
                  ↓
             私钥进行签名
                  │
                  ↓
               广播交易
                  │
                  ↓
             节点验证签名
                  │
                  ↓
             验证交易规则
                  │
                  ↓
               执行交易
                  │
                  ↓
             状态发生变化
```

这就是理解区块链交易非常重要的一条主线。

# 12｜钱包到底保存的是什么？

现在可以回答一个很多新手都会问的问题：

> **“我的钱包里到底装着什么？”**

很多人刚开始会说：

> “我把 ETH 放进 MetaMask 里面了。”

但从区块链的角度看，这种理解并不准确。

链上资产的状态记录在区块链网络中。

而钱包最核心的作用之一，是：

> **帮助用户管理密钥，并使用密钥签署交易。**

所以可以简单理解：

```text
     钱包
      ↓
   管理密钥
      ↓
获得账户控制能力
      ↓
   创建交易
      ↓
  使用私钥签名
      ↓
  发送到区块链
      ↓
  改变链上状态
```

所以你换了一台设备，并不意味着链上的资产跟着原来的手机走了。

只要你能够正确恢复对账户的控制权：

```text
    新的钱包
       ↓
  恢复对应密钥
       ↓
 访问原来的账户
       ↓
读取链上资产状态
```

依然可以看到对应资产。

因此：

> **钱包更像是“管理账户控制权的工具”，而不是一个真正把 Token 装在里面的容器。**

这也是为什么钱包安全如此重要。

# 13｜为什么“私钥泄露”意味着资产可能不安全？

现在我们把整个逻辑串起来。

假设 Alice 有：

```text
100 Token
```

正常情况下：

```text
 Alice
   ↓
拥有私钥
   ↓
创建交易
   ↓
私钥签名
   ↓
网络验证
   ↓
交易执行
```

但是如果攻击者获得了 Alice 的私钥：

```text
   攻击者
     ↓
  获得私钥
     ↓
  创建交易
     ↓
生成有效签名
     ↓
    广播
     ↓
网络验证通过
```

从区块链协议的角度看：

> **只要签名合法，网络通常无法仅凭这套密码学证明判断“操作的人是不是现实中的 Alice”。**

这就是 Web3 和传统互联网账户体系一个非常重要的区别。

传统互联网：

```text
忘记密码
   ↓
找回密码
   ↓
重新登录
```

区块链账户则更加依赖密钥控制。

所以一定要记住：

```text
钱包地址：
可以公开

公钥：
通常可以公开

私钥：
必须保密
```

而且不要把“签名”理解成：

> “反正我没给私钥，随便签名都没关系。”

这同样危险。

因为未来你会遇到：

```text
Token Approve
Permit
智能合约授权
消息签名
```

这些都可能涉及不同形式的签名授权。

所以以后连接陌生网站、点击钱包里的“确认”之前，最好先搞清楚：

> **我到底在授权什么？**

# 14｜把整篇文章浓缩成一张图

如果前面的内容有点多，其实不用全部背下来。

先记住这张图：

```text
                     私钥
                      │
                      │ 密码学计算
                      ↓
                     公钥
                      │
                      │ 地址生成规则
                      ↓
                  钱包地址
```

交易签名：

```text
                  交易数据
                     │
                     ↓
                    哈希
                     │
                     ↓
                  消息摘要
                     │
                     ↓
                  私钥签名
                     │
                     ↓
                  数字签名
                     │
                     ↓
                广播到区块链
                     │
                     ↓
                  节点验证
                     │
                     ↓
                  执行交易
                     │
                     ↓
                状态发生变化
```

最终可以浓缩成五句话：

> **私钥负责控制账户。**

> **公钥由私钥通过密码学算法生成，可以公开。**

> **钱包地址是根据具体区块链规则生成的账户标识，并不等同于公钥。**

> **哈希把交易数据转换成固定长度的摘要，帮助验证数据完整性。**

> **数字签名使用私钥授权交易，网络可以利用公开信息验证签名，而不需要知道私钥。**

如果这五句话你能理解，区块链钱包和交易的底层逻辑就已经迈过了第一道门。

# 15｜下一步：区块链为什么不需要中心服务器？

现在我们解决了一个非常重要的问题：

> **区块链怎么知道一笔交易是不是账户控制者授权的？**

答案是：

```text
  私钥
   ↓
数字签名
   ↓
公钥验证
```

同时：

```text
交易数据
   ↓
  哈希
   ↓
消息摘要
```

帮助系统验证数据是否被篡改。

但是新的问题马上出现了。

假设：

```text
Alice 发起一笔交易
```

交易广播出去之后：

```text
Node A
Node B
Node C
Node D
...
```

这么多节点为什么会相信同一笔交易？

如果不同节点同时收到不同的交易怎么办？

谁负责把交易组织成区块？

如果两个节点对网络状态的理解不一样，又怎么办？

这就进入了区块链的另一个核心问题：

> **分布式网络。**

也就是下一篇：

# 区块链为什么不需要中心服务器？

我们会从最简单的问题开始：

> **如果没有一个中央服务器，到底是谁在维护这条区块链？**

然后继续往下理解：

```text
  单台服务器
      ↓
   多个节点
      ↓
   P2P 网络
      ↓
  分布式维护
      ↓
   共识机制
```

到这里你会开始发现：

**密码学、哈希、钱包、交易、节点、区块、共识、状态**

其实并不是一堆孤立的专业名词。

它们是在共同解决一个问题：

> **如何让一群互不信任的计算机，共同维护一套可以被验证的状态。**
