假如你写了一个链上抽奖合约：100 个人每人交 0.01 ETH，最后抽一个人拿走全部奖金。

规则都写好了，可中奖号码从哪来？链上能凑出来的数字都不靠谱：时间戳能调、区块哈希能提前算、拿哈希搅一下也只是看起来乱。**那到底有没有一个办法，能让所有人都相信“这个中奖号码是随机出来的、没人动过手脚”？**

有。这就是 Chainlink VRF。

> 💡 **先说清楚**：这篇文章讲 Chainlink VRF 的工作原理和在测试网上的完整用法，帮你理解可验证随机数是怎么回事。本文是知识科普，不是投资建议；涉及真金白银的合约逻辑，上线前一定要经过专业审计，先在测试网把流程跑通。

## 一、VRF 到底是什么？一句话：随机数 + 一份谁都能验的证明

VRF 是 Verifiable Random Function 的缩写，翻译过来就是“可验证随机函数”。

先别被这个名字吓到。拆开看就两件事：

- **Random（随机）**：它给你一个随机数。
- **Verifiable（可验证）**：这个随机数后面跟了一份密码学证明，任何人都能验证“这个数字确实是随机生成的，没有被改过”。

光给随机数是不够的。随便哪个中心化服务器都能给你一个随机数，问题是：你怎么知道它没在背后挑一个对自己有利的结果？VRF 的关键，就在“可验证”这三个字上。

打个比方。普通的随机数服务像一个黑箱子：你把手伸进去，它递出来一个号码。你只能选择相信它。

VRF 像一个上了封条的抽奖箱：号码递出来的同时，还附了一张**验真卡**。这张卡上有两样东西：生成这个号码用的公钥，和一个数学证明。任何人拿着这张卡，都能自己算一遍，确认这个号码确实是由那个公钥对应的私钥算出来的、确实对应你这次的请求、确实没有被中途换掉。

```
普通的随机数服务
    │
    ├─→ 你：给我一个随机数
    └─→ 它：7（信不信由你）

Chainlink VRF
    │
    ├─→ 你：给我一个随机数
    └─→ 它：7 ＋ 一份证明
            │
            └─→ 任何人都能验：这个 7 确实是随机生成的，没被换过
```

**所以 VRF 解决的不是“怎么生成随机数”，而是“怎么让所有人相信这个随机数是干净的”。**

在区块链上，这一点比随机本身更重要。因为链上的东西都是公开的、谁都能查的，一个“请相信我”的随机数，在这里是站不住脚的。

## 二、这份证明到底是怎么回事？

要理解证明，得先理解 VRF 背后的两个角色：**私钥和公钥**。

### 每个 VRF 节点都有一对密钥

运行 VRF 服务的 Chainlink 节点，手里有一对密钥：

- **私钥**：只有节点自己知道，用来生成随机数。谁都不知道它是什么，也就谁都算不出它会生成什么数字。
- **公钥**：公开的，所有人都能查到。公钥对应的哈希值，就是你在合约里填的那个 `keyHash`。

节点生成随机数的时候，拿两样东西做输入：

1. **种子**：来自你的请求本身——请求里带的参数，加上请求发出时那个区块的区块哈希。这个种子在你发出请求之前是不存在的，谁也提前不知道。
2. **自己的私钥**：节点用私钥对种子做一次运算，得到两个输出：一个随机数，和一个证明。

### 证明为什么能防作弊？

这个证明有三个作用，一个都不能少：

- **证明数字是私钥算出来的**：证明和公钥是一对，只有持有对应私钥的人才能算出能通过验证的证明。节点想换个数字？换了数字，证明就对不上了，链上的协调器合约会直接拒绝。
- **证明数字对应的是你这次请求**：证明里绑着你这次请求的种子，节点不能拿上一次请求的结果来冒充这一次的，也不能把一个结果重复用在两次抽奖上。
- **证明在数字可用之前就被验过了**：随机数不是先发给你的合约、再慢慢验。流程是反过来的——协调器合约先在链上验证证明，验证通过了，才把随机数回调给你的合约。证明不过，数字根本到不了你手里。

```
你的合约发出请求
    │
    ├─→ 种子 = 请求参数 + 当时的区块哈希（请求前没人知道）
    │
    ├─→ VRF 节点用私钥算出：随机数 + 证明
    │
    ├─→ 协调器合约在链上验证证明
    │      ├─→ 证明有效 → 把随机数回调给你的合约
    │      └─→ 证明无效 → 拒绝，随机数作废
    │
    └─→ 你的合约在 fulfillRandomWords 里收到随机数
```

还有一个细节值得说：**节点自己也改不了结果**。节点在算出随机数之前，不知道种子会是什么——种子里有请求发出时那个区块的区块哈希，而那个区块哈希在请求发出之前并不存在。算出来之后，它又改不了——改了数字，证明就失效。所以官方文档里有一句话说得很直接：结果不能被任何一方操控，包括预言机运营方、合约开发者、用户、矿工和出块者。

当然，凡事都有个但是。官方文档自己也留了一个脚注：如果有人同时偷走了 VRF 的私钥、又能控制目标链的出块，那结果还是可能被影响的。这是个极端假设，现实中几乎不可能同时满足，但知道有这么个边界，比以为它绝对无敌要好。

|  | 链上凑随机数 | 中心化服务器给随机数 | Chainlink VRF |
| --- | --- | --- | --- |
| 随机数从哪来 | 区块时间戳、哈希等公开数据 | 某台服务器的随机数生成器 | 链下节点私钥 + 请求种子 |
| 别人能不能提前算出来 | 能，输入全公开 | 不能，但你得信它 | 不能，私钥是秘密 |
| 操控结果要付出什么 | 出块者调时间戳、丢块 | 服务器直接挑一个结果 | 几乎做不到，证明会失效 |
| 你怎么知道它没作弊 | 没法知道 | 没法知道，只能信 | 自己拿公钥验算证明 |
| 适合什么场景 | 低价值的小事 | 不上链的内部抽奖 | 奖金、稀有 NFT、链上游戏 |

## 三、VRF v2.5：现在该用的版本

Chainlink VRF 也出过好几个版本。现在要记住的只有一句话：**新项目直接用 v2.5，别再用 v1 和 v2 了。**

2024 年 11 月 29 日起，VRF v2.5 正式取代了 v1 和 v2。官方文档里写得很清楚：v2.5 包含了 v2 的全部好处，另外多了两个实用的变化：

- **更容易升级到未来的版本**：协调器的设计留了升级的口子，以后出新版本，迁移的成本更小。
- **可以用 LINK，也可以用链的原生代币付费**：以前只能用 LINK 付，现在 ETH、AVAX 这些原生代币也可以直接付。

写这篇文章的时候（2026 年 11 月），官方文档最新一次更新是 2026 年 11 月 21 日，里面讲的仍然是 v2.5，没有更新的 v3。也就是说，**v2.5 就是目前最新的、该用的版本**。如果你在网上看到有些教程还在用 v1 或者 v2 的写法，那些代码对着现在的协调器是跑不起来的——v1、v2 的合约接口和 v2.5 不一样，照抄会直接报错。

### 两种付费方式：订阅和直接付费

v2.5 有两种用随机数的方式，选哪个主要看你的使用频率：

**订阅（Subscription）**：先开一个订阅账户，往里面充一笔 LINK 或者原生代币，再把你的合约加进这个账户的消费者名单。之后每次请求随机数，费用直接从订阅余额里扣。一个订阅最多可以带 100 个消费合约，适合要经常请求随机数的项目。

**直接付费（Direct Funding）**：不建订阅，每次请求的时候，消费合约自己当场付钱。适合偶尔才需要一次随机数的场景，比如一年只抽一次奖的小项目。

|  | 订阅 | 直接付费 |
| --- | --- | --- |
| 要不要先建账户 | 要，在 vrf.chain.link 上建订阅 | 不要 |
| 费用什么时候扣 | 请求处理完之后，从订阅余额里扣 | 请求的时候当场预估并扣，多付的不退 |
| 一个账户能带几个合约 | 最多 100 个消费合约共用一个余额 | 每个合约自己付自己的 |
| Gas 开销 | 低一些 | 高一些 |
| 适合谁 | 经常要随机数的项目 | 偶尔用一次的场景 |
| 最容易踩的坑 | 余额用完没发现，请求卡住 | 预估少了，请求失败；多付了也不退 |

两种方式都能用 LINK 或者原生代币付。有个细节要注意：**用原生代币付的时候，附加费比例会比用 LINK 高一点**。在以太坊和 Sepolia 上，用 LINK 付附加费是 20%，用 ETH 付是 24%。差得不多，但账要算清楚。

### Sepolia 测试网的配置

这一节的数字，都是从 Chainlink 官方文档的支持网络页面上直接核对过的（2026 年 11 月 23 日查的）。写合约的时候，这些地址和参数是直接抄进代码里的，抄错一个字符，合约就找不到协调器，所以一定以官方文档为准：

| 配置项 | Sepolia 上的值 |
| --- | --- |
| VRF 协调器地址 | 0x9DdfaCa8183c41ad55329BdeeD9F6A8d53168B1B |
| LINK 代币地址 | 0x779877A7B0D9E8603169DdbD7836e478b4624789 |
| Key Hash（500 gwei 档） | 0x787d74caea10b2b357790d5b5247c2f63d1d91572a9846f780606e4d953677ae |
| 最少确认区块数 | 3 |
| 最多确认区块数 | 200 |
| 回调 Gas 上限 | 2,500,000 |
| 单次请求最多随机数个数 | 500 |
| 附加费（用 LINK 付） | 20% |
| 附加费（用 Sepolia ETH 付） | 24% |

里面有几个参数需要解释一下：

- **Key Hash**：就是前面说的那个公钥的哈希值。它还有一个作用是选“Gas 档位”——500 gwei 的意思是，这个档位下每次请求的 Gas 价格上限是 500 gwei。Gas 涨得太厉害的时候，超过这个上限的请求就不会被处理。
- **确认区块数**：请求发出后，要等几个区块才让节点开始算。等得越久，种子里那个区块哈希就越难被操控。Sepolia 上最少是 3 个区块，一般直接用 3 就行。
- **回调 Gas 上限**：你的合约收到随机数之后要执行的逻辑，最多能用多少 Gas。这个值是你自己在请求里定的，不能超过上面那个 2,500,000 的上限。

## 四、VRF 的完整流程：请求—接收两步走

VRF 不是你调一个函数、马上拿到一个数字。它是“请求—接收”两步走的，中间隔了几个区块的时间。理解这个节奏，是用好 VRF 的第一步。

```
你的合约                          VRF 协调器                    VRF 节点（链下）
    │                                  │                              │
    │  ① 发请求                         │                              │
    │  requestRandomWords ──────────→  │                              │
    │  （带上 keyHash、订阅号、确认数、  │                              │
    │   回调 Gas 上限、要几个随机数）    │                              │
    │                                  │  ② 触发事件，                 │
    │                                  │  等确认区块数过去              │
    │                                  │ ──────────────────────────→  │
    │                                  │                              │  ③ 用私钥算出
    │                                  │                              │  随机数 + 证明
    │                                  │  ④ 证明和随机数传回链上       │
    │                                  │  ←────────────────────────── │
    │                                  │  ⑤ 协调器在链上验证证明       │
    │                                  │  证明有效？                   │
    │  ⑥ 回调 fulfillRandomWords        │                              │
    │  ←────────────────────────────── │                              │
    │  你的合约拿到随机数，执行业务逻辑  │                              │
```

整个流程里，你的合约要做三件事：

1. **继承 `VRFConsumerBaseV2Plus`**：这是 Chainlink 提供的基类，v2.5 的消费合约都要继承它。注意名字里有个 `Plus`，v2 的 `VRFConsumerBaseV2` 在 v2.5 的协调器上是不能用的。
2. **调用 `requestRandomWords` 发请求**：把 keyHash、订阅号、确认区块数、回调 Gas 上限、要几个随机数这几个参数传进去，拿到一个请求编号 `requestId`。
3. **实现 `fulfillRandomWords` 回调**：随机数到了之后，协调器会自动调你合约里的这个函数，你的业务逻辑——比如算中奖号码、发奖——都写在这里面。

注意一个经常犯的错：**随机数不会在发请求的那笔交易里回来**。请求和接收是两笔不同的交易，中间隔了几个区块。所以业务逻辑不能写在发请求的函数里，一定要写在回调里。把抽奖逻辑写在请求函数里、以为随机数已经到手了，是新手最容易踩的坑之一。

## 五、动手：在 Sepolia 上跑一遍

理论讲完了，接下来按官方文档的入门教程，在 Sepolia 测试网上把整个流程走一遍。需要的东西不多：一个装了 Sepolia ETH 的 MetaMask 钱包、Remix、还有一点测试网 LINK。

### 第 1 步：建订阅、充钱、加消费者

打开 vrf.chain.link，连上 MetaMask（切到 Sepolia 网络），创建一个订阅。建好之后会得到一个订阅号，记下来。

然后给订阅充钱：测试网 LINK 和 Sepolia ETH 都可以从 faucets.chain.link 领。充多少合适？先充个 5 个测试 LINK 练手就够了，跑几次请求完全够用。

最后一步很关键，也最容易忘：**把你的消费合约地址加进订阅的消费者名单**。合约还没部署？没关系，先部署合约，再回来加。顺序反了也没事，只要在第一次发请求之前加好就行。

### 第 2 步：写消费合约

下面这份代码是按官方文档的入门示例改的，核心逻辑没变，只加了中文注释。先看整体，再一段段拆：

```
import {VRFConsumerBaseV2Plus} from "@chainlink/contracts/src/v0.8/vrf/dev/VRFConsumerBaseV2Plus.sol";
import {VRFV2PlusClient} from "@chainlink/contracts/src/v0.8/vrf/dev/libraries/VRFV2PlusClient.sol";

contract VRFD20 is VRFConsumerBaseV2Plus {
    uint256 s_subscriptionId;
    address vrfCoordinator = 0x9DdfaCa8183c41ad55329BdeeD9F6A8d53168B1B;
    bytes32 s_keyHash = 0x787d74caea10b2b357790d5b5247c2f63d1d91572a9846f780606e4d953677ae;
    uint32 callbackGasLimit = 100000;
    uint16 requestConfirmations = 3;
    uint32 numWords = 1;

    uint256 public s_randomWord;
    uint256 public s_requestId;

    constructor(uint256 subscriptionId)
        VRFConsumerBaseV2Plus(vrfCoordinator)
    {
        s_subscriptionId = subscriptionId;
    }

    function rollDice() external {
        s_requestId = s_vrfCoordinator.requestRandomWords(
            VRFV2PlusClient.RandomWordsRequest({
                keyHash: s_keyHash,
                subId: s_subscriptionId,
                requestConfirmations: requestConfirmations,
                callbackGasLimit: callbackGasLimit,
                numWords: numWords,
                extraArgs: VRFV2PlusClient._argsToBytes(
                    VRFV2PlusClient.ExtraArgsV1({nativePayment: false})
                )
            })
        );
    }

    function fulfillRandomWords(uint256 requestId, uint256[] calldata randomWords) internal override {
        s_randomWord = randomWords[0];
    }
}
```

一段段看：

- **开头两个 import**：一个是基类 `VRFConsumerBaseV2Plus`，一个是帮你拼请求参数的库 `VRFV2PlusClient`。v2.5 的请求参数是打包成一个结构体传进去的，不像 v2 那样一个个传。
- **几个写死的配置**：协调器地址和 keyHash 就是上一节那个表里的 Sepolia 的值，直接抄。`callbackGasLimit` 设了 100000——这个例子里的回调只做了一件事，就是把随机数存下来，10 万 Gas 绰绰有余。`requestConfirmations` 是 3，也就是 Sepolia 的最少值。`numWords` 是 1，只要一个随机数。
- **构造函数**：把订阅号传进来，同时把协调器地址传给基类。部署的时候，订阅号要填你第 1 步建的那个。
- **`rollDice` 函数**：这就是发请求的地方。`nativePayment: false` 的意思是这次用 LINK 付费。想改用 Sepolia ETH 付？把这个值改成 `true` 就行，不过记得附加费会从 20% 变成 24%。
- **`fulfillRandomWords` 回调**：随机数到了，协调器自动调这个函数。这里只是把第一个随机数存进了 `s_randomWord`。真正做抽奖的时候，开奖逻辑就写在这里——比如用这个随机数对 100 取模，得到中奖号码。

### 第 3 步：部署、请求、等回调

在 Remix 里编译、部署到 Sepolia。部署的时候填订阅号。部署完别忘了回 vrf.chain.link，把这个新合约的地址加进订阅的消费者名单。

然后调一次 `rollDice`。这笔交易上链之后，你会拿到一个 `requestId`。接下来等几个区块——Sepolia 出块大概 12 秒一个，3 个确认区块加上节点生成和验证的时间，通常一分钟左右，回调就会到。去合约里读 `s_randomWord`，如果不再是 0，说明随机数已经到了。

可以在 Sepolia Etherscan 上搜你的合约地址，看到整个过程留下的两笔交易：**一笔是你发请求的，一笔是协调器回调你的**。这就是“请求—接收”两步走在链上的样子。

## 六、费用是怎么算的？

用 VRF 是要付钱的。费用分两部分：

```
一次 VRF 请求的总费用
    │
    ├─→ Gas 成本 = Gas 价格 ×（验证 Gas + 回调 Gas）
    │      验证 Gas：协调器在链上验证证明要花的 Gas
    │      回调 Gas：你的 fulfillRandomWords 执行要花的 Gas
    │
    └─→ 再乘以（100 + 附加费比例）/ 100
           用 LINK 付：附加费 20%
           用 Sepolia ETH 付：附加费 24%
```

订阅方式下，费用是在请求处理完之后才从订阅余额里扣的。扣之前，系统会先按你设的上限预留一笔“最高可能费用”（在订阅管理页面上显示为 Max Cost），防止 Gas 突然涨价导致扣费失败。实际扣的钱一般比预留的少，差额会留在你的订阅余额里。

有几个跟钱有关的点，新手经常搞不清楚：

- **Gas 价格用的是哪一档？** 是你选的 keyHash 对应的档位。Sepolia 上那个 500 gwei 的 keyHash，意思就是 Gas 价格最高按 500 gwei 算。Gas 真涨到 500 gwei 以上，你的请求就排不上队了。
- **回调 Gas 设多少合适？** 看你的回调里要干多少事。只存一个数字，10 万够了；回调里要发奖、要改好几个 NFT 的属性，那就得往上加。设小了，回调执行到一半 Gas 用完，整个回调回滚，随机数就白白浪费了——钱照扣，事没办成。
- **订阅余额要留多少？** 至少留够几次请求的钱，别卡着最低余额过日子。余额用完了，新的请求不会被处理，抽奖会在那等着，用户那边看到的就是“点了抽奖没反应”。

## 七、新手最容易踩的坑

把上面这些串起来，列一张检查清单。写 VRF 合约之前，先对着过一遍：

1. **把回调当成同步调用。** 随机数不会立刻回来，业务逻辑必须写在 `fulfillRandomWords` 里，不能写在发请求的函数里。这是 VRF 的头号坑，前面第四节讲流程的时候也提过一次。
2. **用了 v2 的基类和接口。** `VRFConsumerBaseV2` 是 v2 的，v2.5 要用 `VRFConsumerBaseV2Plus`。名字只差一个词，编译的时候就会报错，报错信息还不太直观。
3. **订阅里忘了加消费合约。** 订阅建了、钱充了、合约也部署了，一调请求就失败——十有八九是消费者名单里没有你的合约地址。每次部署新合约，都要回来加一次。
4. **订阅余额用完了。** 余额一空，请求就卡住。抽奖、开奖这种有时效的事，卡住就是事故。上线前算好余额，设个提醒。
5. **回调 Gas 上限设得太小。** 回调执行到一半没 Gas 了，整笔回调回滚，随机数作废，费用照扣。回调里每多一件事，都要重新估算。
6. **确认区块数设得太低。** 确认数越低，请求处理得越快，但种子被操控的难度也越低。Sepolia 上最少 3 个，一般直接用 3；主网高价值的场景，可以往上加。
7. **一次要太多随机数。** 单次请求最多 500 个，听着很多，但每个随机数都要多花 Gas 和钱。抽奖要 100 个号码？一次要 100 个没问题，但先算算账，别闭着眼睛要 500 个。
8. **在测试网测得好好的，就直接上主网。** 测试网的 Gas 价格、附加费、LINK 价格都和主网不一样。主网的协调器地址、keyHash 也都不一样，照抄 Sepolia 的配置部署到主网，合约根本找不到协调器。
9. **以为 VRF 能解决所有随机问题。** VRF 解决的是“随机数可不可信”，不是“抽奖公不公平”。抽奖规则本身写得有问题——比如中奖概率算错了、有人能重复参加——VRF 也救不了你。

**一句话：VRF 是目前链上随机数的标准答案，但它是个工具，不是护身符。请求—接收的节奏、订阅和回调的配置、费用的账，每一项都要自己算清楚。**

## 总结

- VRF 是“可验证随机函数”：给你的不只是一个随机数，还有一份密码学证明，任何人都能验证这个数字确实是随机生成的、没有被改过。
- 证明的原理是：VRF 节点用只有自己知道的私钥，对“请求参数 + 当时区块哈希”这个种子做运算，得到随机数和证明；协调器合约先在链上验过证明，才把随机数回调给你的合约。节点自己也改不了结果。
- 现在该用的是 VRF v2.5（2024 年 11 月 29 日起取代 v1 和 v2），截至 2026 年 11 月官方文档的最新版本仍然是 v2.5，没有更新的 v3。
- v2.5 有两种付费方式：订阅适合经常请求，一个订阅最多带 100 个消费合约；直接付费适合偶尔用一次。两种方式都能用 LINK 或原生代币付，用原生代币付附加费更高一点（以太坊和 Sepolia 上是 24%，LINK 是 20%）。
- Sepolia 的配置要以官方文档为准：协调器 0x9DdfaCa8183c41ad55329BdeeD9F6A8d53168B1B，500 gwei 的 keyHash 是 0x787d74caea10b2b357790d5b5247c2f63d1d91572a9846f780606e4d953677ae，最少确认 3 个区块，回调 Gas 上限 250 万，单次最多 500 个随机数。
- 用 VRF 是“请求—接收”两步走：继承 `VRFConsumerBaseV2Plus`，调 `requestRandomWords` 发请求，在 `fulfillRandomWords` 回调里写业务逻辑。随机数不会在发请求的那笔交易里回来。
- 费用 = Gas 价格 ×（验证 Gas + 回调 Gas）×（1 + 附加费比例）。回调 Gas 设小了会回滚、订阅余额用完会卡住、忘了加消费者会请求失败，这三件事最常见。
