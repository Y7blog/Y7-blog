假如你要在链上做一个抽奖：100 个人每人交 0.01 ETH，最后抽一个人拿走全部奖金。

规则写进智能合约，听起来很公平，对吧？可问题马上就来了：**这个中奖号码，到底由谁来定？**

合约自己掷骰子吗？它掷出来的那个数字，全网几千个节点都得认，任何人都能提前算出来——那还叫随机吗？找个链上的数字凑合一下？时间戳、区块哈希、区块号，看起来都挺随机的，可这些数字要么是公开的，要么是出块的人能动手脚的。

这篇就讲这个看起来简单、实际很要命的问题：**区块链为什么不能直接生成随机数？**

> 💡 **先说清楚**：这篇文章讲的是随机数在区块链上的安全问题，帮你理解为什么有些写法一定不能用。本文是知识科普，不是投资建议；涉及真金白银的合约逻辑，上线前一定要经过专业审计。

## 一、区块链的第一条铁律：所有节点必须算出同一个结果

先回到第 1 篇那个比喻：区块链是一台全网共享的状态机。

一笔交易进来，全网几千个节点各自独立执行同一份合约代码，最后必须得到**完全相同的状态**。你的余额变了多少、那个 NFT 归谁了、奖金发给谁了——每个节点算出来的结果必须一模一样，否则共识就达成不了，链就分叉了。

```
同一笔交易
    │
    ├─→ 节点 A 执行合约 ─→ 状态 X
    ├─→ 节点 B 执行合约 ─→ 状态 X
    ├─→ 节点 C 执行合约 ─→ 状态 X
    │
    └─→ 所有结果必须相同，否则无法共识
```

这就是区块链的确定性：**同样的输入，永远得到同样的输出。**

而“随机”恰恰相反：随机就是同样的输入，每次得到不一样的输出。一个要求每次都一样，一个要求每次都不一样——这两件事在同一台机器上，天生就是冲突的。

**所以问题不是“区块链的随机数做得不够好”，而是“区块链的设计从一开始就不允许链上出现真正的随机”。**

## 二、普通程序的随机数，是从哪来的？

你手机上的抽奖 App、电脑里的游戏，随机数是怎么来的？

它们用的是伪随机数生成器（PRNG）：给一个初始的“种子”，再按固定算法算出一串看起来随机的数字。种子本身来自系统里各种带噪声的东西：精确到纳秒的系统时间、鼠标移动、键盘敲击间隔、硬件传感器的噪声。

关键点在于：**这些种子是每台机器自己的秘密。** 你的电脑用什么时间做种子，别人不知道，也没法复算。

|  | 普通程序 | 智能合约 |
| --- | --- | --- |
| 随机数的种子从哪来 | 系统时间、硬件噪声、用户操作 | 只能读链上的公开数据 |
| 别人能不能看到种子 | 看不到，是本机的秘密 | 全网都能看到，完全公开 |
| 别人能不能复算结果 | 不能，不知道种子 | 能，照着合约代码算一遍就行 |
| 每次运行结果一样吗 | 不一样，种子每次都不同 | 必须一样，否则节点无法达成共识 |

智能合约没有自己的秘密。它能读到的所有东西——区块数据、交易内容、自己的存储、调用者的地址——**全网所有人都能看到，而且所有节点都必须算出同一个结果。**

这就注定了：只要随机数是在链上算出来的，它就不可能是秘密。不是秘密的随机数，就不叫随机数，顶多叫“看起来随机的公开数字”。

## 三、时间戳、区块哈希：看起来随机，其实全是公开信息

很多新手第一次写抽奖合约，都会写出下面这种代码：

```
function badRandom() public view returns (uint256) {
    return uint256(keccak256(abi.encodePacked(
        blockhash(block.number - 1),
        block.timestamp,
        msg.sender
    )));
}
```

这段代码跑出来的数字，看起来确实乱七八糟、毫无规律。但问题不在“看起来乱不乱”，而在**攻击者能不能提前算出同一个数字**。答案是：能，而且很容易。

### 时间戳：出块的人说了算

`block.timestamp` 是出块的验证者填的。虽然不能乱填——必须比上一个块的时间晚、也不能离现在太远——但在这个小范围内，验证者是可以挑一个对自己有利的值的。

如果奖金足够大，验证者完全可以算一算：这个时间戳出的中奖号码是不是我？不是？那就换一个时间戳，或者干脆把这个块丢掉不出，等下一个机会。

### 区块哈希：只能查最近 256 个块，超了就返回 0

`blockhash(n)` 只能查到最近 256 个区块的哈希。超过这个范围的，或者还没产生的区块，返回的都是 0。

这就埋了两个坑：

- **出块者先知道答案。** 当前块的哈希在块产生之前没人知道，但产生这个块的验证者自己是知道的——他可以在块里先算一遍，看看中奖的是不是自己。
- **拖过 256 个块就只剩 0。** 如果合约的逻辑允许拖延，等目标区块超出 256 个块的窗口，`blockhash` 返回的就是固定值 0，所谓的随机数变成了一个人人皆知的常数。

### 区块号、调用者地址：攻击者自己就能控制

`block.number` 是公开递增的数字，没有任何秘密可言。`msg.sender` 更直接——攻击者完全可以换个地址、换个账户 nonce，再算一遍，直到算出一个对自己有利的结果再动手。

### keccak256：把公开的东西搅乱，不等于保密

最容易踩的坑是这个：很多人觉得，把几个公开数字用 `keccak256` 哈希一下，出来的结果谁也猜不到，那就安全了。

错了。哈希只能把输入变得“看不出来”，但**输入本身是公开的，任何人都能拿同样的输入、跑同样的哈希，得到完全一样的输出**。看起来乱，不代表算不出来。

更要命的是攻击的成本极低。攻击者可以自己写一个合约，在同一笔交易里先把中奖结果算一遍：

```
攻击者合约的思路
    │
    ├─→ 先按目标合约的公式，把中奖号码算出来
    ├─→ 中了 → 真正下注，拿走奖金
    └─→ 没中 → 直接 revert，整笔交易作废，只损失一点 Gas
```

不中就撤回，只付 Gas；中了就拿走奖金。这根本不是抽奖，这是**拿着答案去考试，还能无限次重考**。

| 常见的链上“随机数来源” | 能不能被预测 | 谁能动手脚 | 结论 |
| --- | --- | --- | --- |
| block.timestamp | 能，全网可见 | 出块的验证者可在小范围内调整 | 不能用 |
| blockhash | 能，历史块哈希公开 | 出块者先知道；超 256 块返回 0 | 不能用 |
| block.number | 能，完全公开 | 无人能改，但毫无秘密 | 不能用 |
| msg.sender / nonce | 能，攻击者自己控制 | 攻击者换地址重算 | 不能用 |
| keccak256(以上任意组合) | 能，输入公开就能复算 | 哈希掩盖不了公开的输入 | 不能用 |

**一句话总结：链上所有数据都是公开的，公开数据算出来的“随机数”，只是还没被人算过的随机数。**

## 四、block.prevrandao：进步了一大步，但还是不够

以太坊合并（The Merge）之后，事情有了一点转机。

原来的 `block.difficulty`（挖矿难度）在合并后被改成了 `block.prevrandao`，Solidity 0.8.18 开始可以直接用。这个值来自信标链的 RANDAO 机制：每个出块的验证者用自己的私钥对 epoch 编号做一次签名，把签名结果异或进一个累加器，所有验证者的贡献混在一起，就是这个 RANDAO 值。

它比时间戳强在哪？**这个值在出块前一个 slot 就已经定下来了**，不像时间戳那样，出块的人还能临场挑一个对自己有利的数字。

但它仍然不够安全，原因出在“最后一个揭示者”身上：

```
一个 epoch 有 32 个 slot
    │
    ├─→ 前 31 个 slot 的验证者依次贡献，累加值不断变化
    │
    └─→ 第 32 个 slot 的验证者出块时
         已经能看到前面 31 个人的累加结果
         他可以选择：出这个块（接受结果）
                     或者跳过这个 slot（改变结果，代价是丢掉出块奖励）
```

也就是说，最后一个出块的人，对结果有 **1 bit 的影响力**：出，还是不出。如果他控制了连续多个 slot，影响力还会更大。奖金够大的时候，丢掉一次出块奖励去换一个中奖号码，这笔账验证者是会算的。

EIP-4399（引入 prevrandao 的提案）自己也留了个口子：它建议应用不要直接用当下的值，而是**往后看几个 epoch 再采样**，比如隔 4 个 epoch（大约 25 分钟）之后再用，让攻击者在下注的时候还不知道最终结果。

所以对 `block.prevrandao` 的判断是这样的：

- **低价值的场景**（比如抽个头像框、决定游戏里的小奖励），用它凑合一下，风险可以接受。
- **高价值的场景**（奖池、稀有 NFT、真金白银的抽奖），绝对不能只靠它——验证者一算账，就可能宁可丢块也要改结果。

**prevrandao 是目前链上能拿到的最好的“半随机”来源，但“半随机”在高价值场景里，和“不随机”没有本质区别。**

## 五、真实教训：2018 年，EOS 上的博彩游戏接连被搬空

这不是纸上谈兵。2018 年，EOS 上的一批博彩类 dApp，就是因为随机数可预测，被攻击者轮番收割。

| 事件 | 时间 | 损失 | 原因 |
| --- | --- | --- | --- |
| EOSBet 第一次被盗 | 2018 年 9 月 | 约 4 万 EOS（约 20 万美元） | 随机数生成逻辑可预测 |
| EOSBet 第二次被盗 | 2018 年 10 月 | 约 6.5 万 EOS（约 33.8 万美元） | 同类问题，一个月内第二次被盗 |
| BetDice 被盗 | 2018 年 12 月 18 日 | 约 20 万 EOS | 攻击者只提交会赢的交易 |
| EOSBet 两次合计 | 2018 年 9–10 月 | 超过 100 万美元 | 随机数问题反复被利用 |

攻击的手法，和上一节讲的一模一样：攻击者先把随机数的生成逻辑反推出来，算好哪一注会赢，再动手。赢的提交，输的直接撤回。EOSBet 在一个月内被盗两次，说明问题不是某一次疏忽，而是**随机数方案本身就不成立**。

这些项目当时都请过审计、都觉得自己的合约“很安全”。但安全审计能查出代码写错了没有，查不出“随机数”这个概念本身在链上就是不成立的。

**这是经常犯的错：把“看起来随机”等同于“不可预测”。** 这两个词在链上，差的不是一点点，差的是一次被盗的全部奖金。

## 六、正确的思路：随机数不能在链上“算”，要从链下“拿”

既然链上算不出安全的随机数，答案只能是：**去链下生成，再把结果和证明一起拿回链上。**

一个能用的随机数方案，必须同时满足三个条件：

1. **不可预测**：在结果公布之前，谁也算不出来，包括生成它的人。
2. **不可操控**：没有人能在看到结果之后改主意、重来一次。
3. **可验证**：任何人都能验证这个数字确实是随机生成的、没有被动手脚。

常见的几种做法，对比一下：

| 方案 | 怎么做 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Commit-Reveal（提交-揭示） | 参与者先提交哈希承诺，之后再公开原始数字，全部异或得到结果 | 不依赖第三方，完全去中心化 | 需要多笔交易；最后揭示的人可以耍赖不公开 |
| Chainlink VRF | 链下生成随机数 + 密码学证明，链上验证证明后再回调 | 可验证、不可操控，行业标准 | 需要付费（LINK 或原生代币），有两次交易的延迟 |
| 随机信标（如 drand） | 多个独立节点用门限签名定期产生公开随机数 | 去中心化程度高，定期产出 | 需要信任信标运营方集合；和合约的集成相对复杂 |
| VDF（可验证延迟函数） | 强制算一段无法加速的计算，算完才知道结果 | 最后一个揭示者来不及在截止前算出结果 | 计算成本高，工程上比较复杂 |

其中最常用的是 **Chainlink VRF（可验证随机函数）**。它的流程是“请求—接收”两步：

```
你的合约
    │
    ├─→ ① 请求随机数：调用 VRF 协调器，交一笔费用
    │
    ├─→ ② 链下生成：Chainlink 节点生成随机数 + 密码学证明
    │
    ├─→ ③ 链上验证：协调器验证证明确实有效、确实对应这次请求
    │
    └─→ ④ 回调你的合约：fulfillRandomWords 收到随机数，继续执行业务逻辑
```

关键点在于第 ③ 步：随机数附带一个密码学证明，任何人都能验证这个数字确实是由 VRF 的私钥算出来的、没有被篡改过。生成随机数的人自己也改不了结果——因为私钥对应的公钥是公开的，改了数字，证明就对不上了。

目前用的是 **VRF v2.5**：2024 年 11 月 29 日起取代了 v1 和 v2。两个实用的变化：

- **两种付费方式**：可以预先充一个订阅账户（多个合约共用），也可以让消费合约每次请求时直接付费。
- **两种支付代币**：LINK 或者链的原生代币都可以付，不过用原生代币付的时候，附加费比例会比用 LINK 高一点。

合约层面要做的事也不多：继承 `VRFConsumerBaseV2Plus`，实现 `fulfillRandomWords` 回调函数，调用 `requestRandomWords` 发请求，剩下的交给协调器和链下节点。

另外提一句方向：Chainlink 正在把这类链下计算统一收进 **CRE（Chainlink Runtime Environment）**——就是 33、34 篇里讲过的、接替 Automation 的那个新环境。随机数这类“链下算、链上验”的工作，以后也会更多地跑在 CRE 上。具体的变化，留到第 45 篇讲 Functions 的时候再展开。

## 七、新手最容易踩的坑

写随机数逻辑之前，先对着下面这张清单过一遍：

1. **用 `block.timestamp` 做抽奖。** 这是最常见的写法，也是最容易被利用的写法。验证者能调时间戳，攻击者能提前算结果。
2. **觉得哈希一下就安全了。** `keccak256` 只能把公开输入变得看不出来，不能把公开输入变成秘密。输入公开，结果就公开。
3. **用 `blockhash` 却不检查返回值。** 超过 256 个块的范围，`blockhash` 返回 0。合约一旦允许拖延，随机数就变成了一个固定值。
4. **拿 `block.prevrandao` 当万能钥匙。** 它只适合低价值场景。奖池一大，验证者丢块改结果的动机就上来了。
5. **在测试网测得好好的，就直接上主网。** 测试网的验证者没有经济动机去操控你的抽奖，主网有。测试网能跑通，不等于主网安全。
6. **把 VRF 的回调当成同步调用。** VRF 是“请求—接收”两步走的，随机数不会立刻回来。业务逻辑要写在 `fulfillRandomWords` 回调里，不能在请求的那笔交易里就假设已经拿到了结果。
7. **忘了给 VRF 订阅充值。** 订阅余额用完了，请求就不会被处理，抽奖会卡住。订阅余额和回调 Gas 上限，都要在上线前算清楚。

**一句话：凡是奖金、稀有 NFT、排名这些有价值的东西，随机数一律走 VRF 这类可验证的链下方案，不要在链上自己凑。**

## 总结

- 区块链是确定性状态机：同样的输入，全网节点必须算出同样的输出。这和“随机”天生冲突，所以链上没有真正的随机数。
- 普通程序的随机数靠每台机器自己的秘密种子，智能合约没有秘密——它能读到的所有东西全网可见、都能复算。
- `block.timestamp`、`blockhash`、`block.number`、`msg.sender` 这些链上数据全是公开的，攻击者可以在同一笔交易里先算一遍，不中就撤回，只损失 Gas；验证者也可以丢掉不利的块重出。
- `keccak256` 只是把公开输入搅乱，看起来乱不代表算不出来；`blockhash` 超过 256 个块返回 0，是一个现成的坑。
- `block.prevrandao`（EIP-4399，Solidity 0.8.18 起可用）比时间戳强，但最后一个出块者仍有 1 bit 的影响力，只适合低价值场景。
- 真实教训：2018 年 EOSBet 一个月内两次被盗、合计超 100 万美元，BetDice 一天被盗约 20 万 EOS，根子都是随机数可预测。
- 正确的思路是链下生成、链上验证：Chainlink VRF v2.5 是目前最常用的标准方案，支持订阅和直接付费、LINK 或原生代币支付；Chainlink 也在把这类链下计算统一收进 CRE。
